## Implementation (`src/range.js:1`)

Replaced the naive `split('..')` + `Number()` approach with an anchored regex plus explicit contract checks:

- **Anchored pattern** `/^(-?\d+)\.\.(-?\d+)$/` — enforces *exactly* `start..end` with base-10 digits. This alone fixes the largest class of bugs: `split('..')` silently accepted `2..7..9`, `2...7`, `0x10..20`, `1e2..300`, and internal whitespace (`Number(' 2 ')` coerces fine).
- **Bounds check** against ±100000 for both endpoints.
- **Ordering check** `start > end` → `null`.
- **`-0` normalization** so `-0..0` can't leak a negative zero into the returned object.

`value.trim()` handles the surrounding-whitespace allowance; the `typeof` guard and named export are preserved.

## Tests (`test/range.test.mjs`)

Kept the original four, added 16 focused cases: inclusive bounds and just-outside-bounds (±100001), equal endpoints, reversed negatives, decimals, non-string inputs (incl. `NaN` and `Symbol`), empty/whitespace-only, missing endpoints, wrong/repeated separators, internal whitespace, leading/trailing junk, non-decimal numeric forms, malformed signs, and object shape.

## Two judgment calls worth flagging

The README doesn't specify behavior for **explicitly signed positives** (`+2..7`) or **leading zeros** (`007..010`). My implementation rejects the former and accepts the latter, but I deliberately did *not* assert either in the tests — encoding a guess as a requirement would be worse than leaving it uncovered. The `-0..0` test is likewise written to tolerate `null`, asserting only that *if* a range comes back it has no negative zero. If you want a definitive answer on those, that's a contract decision for the README.
